The slot model is how slotsmith components are built: each is made of named slots, and its `components` prop replaces any of them. An element part receives one element's props; a widget part is told the state and renders what it likes. Slots you leave alone keep their fallbacks.

## Two kinds

**Element parts** stand for one element. `<Row>` gets the props of a `<tr>`, `<Cell>` those of a `<td>`, `<Root>` those of a `<div>`. Pass a component that renders that element and spread every prop onto it: they carry the classes, the `data-*` state below, the handlers and the ARIA attributes the table relies on.

<SampleCode name="guides/element-part" />

A component that already takes those props, such as shadcn/ui's `TableRow` or MUI's `TableRow`, fits as it is: `components={{ Row: TableRow }}`. `<DragHandle>` is an element part too, a `<button>` whose props are the row reorder engine's handlers, so spreading them is what makes the drag work.

**Widget parts** stand for a control. `{Checkbox}` gets `checked`, `indeterminate`, `disabled`, `onCheckedChange` and its `aria-label`; `{Pagination}` gets the page, the page count, whether a previous or next page exists and the functions that go there. The markup is yours, so a design system's own checkbox or pager plugs in through a small adapter.

<SampleCode name="guides/widget-part" />

The data table has 12 element parts and 10 widget parts. Each slot's props are listed on the [API page](../components/data-table/api/#slots), and the [adapters](../components/data-table/adapters/) show the full maps for five design systems.

## Data state

Element parts show their state as `data-*` attributes rather than class names, so you style them with attribute selectors and any design system that already reads them (shadcn/ui's `TableRow` styles `data-[state=selected]`) picks them up. From the data table's source:

- `<Root>`: `data-status` is `loading`, `error`, `empty` or `ready`; `data-size`, `data-striped`, `data-virtual` for the virtual table, and `aria-busy` while loading.
- `<HeaderCell>`: `data-sorted` is `asc` or `desc` on the sorted column, beside `aria-sort`; `data-align` follows the column's `meta.align`.
- `<Row>`: body rows carry `data-state="selected"`, `data-depth`, `data-expanded` (`true` or `false` on rows that can expand), `data-clickable` with `onRowClick`, and `data-row-id`. During a drag they add `data-dragging`, `data-dragging-child`, `data-drop-position` and `data-drop-edge`. The status rows carry `data-state="loading"`, `"empty"` or `"error"`.
- `<Cell>`: `data-align`, and `data-slot="select"` or `"drag"` on the checkbox and drag-handle cells.

<SampleCode name="guides/data-state" />

Widget parts get the same facts as props instead, such as the `direction` of `{SortIcon}`. The API page lists every attribute under its slot.

## Wrap fallbacks

The built-in parts are exported as `fallbackComponents`. To change one thing about a part, render its fallback inside your own component rather than rewriting it: add a class, put something around it, or pass different props.

## Once, for the whole app

To replace a slot everywhere, set it once on `SlotsmithProvider` instead of on every component. Its `components` prop takes one map per component, under the keys `dataTable`, `autocomplete`, `datePicker` and `fileUploader`. Each is the same map that component's own `components` prop takes, so an [adapter](../components/data-table/adapters/) works in either place.

Below, one provider gives every data table a round checkbox and the date picker a diamond icon. The second table passes its own `Checkbox`, and that one wins:

<Demo name="guides/provider-components" lang="en" height="35rem" />

Each slot resolves on its own, in three layers, and the later one wins:

1. The built-in fallback.
2. The `components` of the providers above, for that component.
3. The component's own `components` prop.

- **Nested providers merge.** An inner provider adds to the outer one component by component, then slot by slot: its slots win, and what it does not name is inherited.
- **The variants read the same maps.** `VirtualDataTable`, `VirtualAutocomplete` and `VirtualFileUploader` use their component's key, and so does a layout built from the compound parts.
- **The page-size select follows `autocomplete`.** The data table's built-in page-size select is a slotsmith `Autocomplete`, so it renders with the provider's `autocomplete` slots. A `PageSizeSelect` slot, from `dataTable` or the table's own prop, replaces it altogether.
- **Keep the map's identity.** Define it outside your component, as the sample does, or memoize it. `slotProps` stay on each component.

`SlotsmithProvider` and the types `SlotsmithComponents` and `SlotsmithComponentName` come from `slotsmith/provider`. The same provider sets the [language](../languages/#passing-a-locale).

## Compound parts

`<DataTable>` is a fixed layout: a root holding the table and the pagination. For another layout, build it from the compound parts inside `DataTable.Provider`. The provider takes the data, the state options and `components`, `labels`, `locale`, `slotProps` and `onRowClick`, and renders no element of its own; `size`, `striped` and HTML attributes go on `DataTable.Root`, and `hidePagination` belongs to `<DataTable>` alone (leave `DataTable.Pagination` out instead). The parts are `DataTable.Root`, `DataTable.Table`, `DataTable.Head`, `DataTable.Body`, `DataTable.Foot`, `DataTable.Row`, `DataTable.StatusRows`, `DataTable.Pagination` and `DataTable.DragHandle`. `useDataTableContext()` reads the same model from any component among them.

## Headless hooks

Under every component is a hook with the state and no markup: `useDataTable`, `useAutocomplete`, `useDatePicker` and `useFileUploader`, each exported from its component's entry. `<DataTable>` calls `useDataTable` for you; call it yourself when no slot replacement gets you the markup you need.

The hook returns the TanStack Table instance, the `status` and the `selection`, and runs row reorder for markup of your own. The data table's [headless hook guide](../components/data-table/guides/headless-hook/) covers it in full.

## Rules

- **A custom `Row` keeps a stable identity.** Define slot components outside the component that renders the table, or memoize the `components` map. A component written inline in `components={{ Row: (props) => <tr {...props} /> }}` is a new type on every render, so React remounts every row: focus, a running drag and any state inside the row are lost.
- **Spread what an element part receives.** Leaving out props drops the `data-*` state, the handlers or the accessible names.
- **Widget parts get told what is true, not what to render.** A widget part decides its markup from the facts it receives (`checked`, `pageCount`, `direction`) and reports back through the callbacks it is given (`onCheckedChange`, `nextPage`), rather than reaching into the table.
- **Keep the accessible names.** Widget parts receive their `aria-label` from the labels; pass it to the control that takes focus.
